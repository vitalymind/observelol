## Project description
OberveLoL (League of Legends Observer) is an app that serve dual purpose:
- **allowing administrator to adjust properties of `Heroes`** and
- **Observing ongoing games and record events for analyzis**.

`Producers` (_Python scripts simulating activity_) concurrently connect to application via restfull API to register new games and send game realated events, such as player picking a Hero, Hero leveling up, Hero buing an item, game concluding with one of the sides winning, etc. Role of `producers` is to generate bursts of messages and to generate data quickly, as well as have a way to stress test system limits.

`Administrators` are able to change properties of `Heroes` and `Items` at any point in time, any changes made to Heroes and `Items` are broadcasted to other `administrators` via SSE. Client application (front) is using delta sync cache, stored in browser localstorage, to minimise database quering.

Application allow concurrency, such that changing Hero and Item stats is allowed at any time. Games that are currently ongoing would not be affected, while future games would pick up latest versions of Heroes and Items.

Ongoing games are available as live feed, with events streamed to `Administrators` using SSE. History of past games is brawsable and analytic tools are available.

## Simulated load
To simulate real environment, a python script is running using Locust to fire many thousands of requests from ideally distributed network or at least from dev machine.

### Concept of game
Game is a simulated load, designed to be flexible in length, usually about several minutes. Game managers `Producers` run games as Python scripts, firing hundreds of events per game via restful API. `Producers` will request GET game_id before start of each game. `Producers` will append game_id to each event, this way events can be identified and assembled. `Producers` will not batch events, but stream (POST) over http/2 keepalive connection, this is only optimisation on `Producer` side allowed. Load will be modulated by both changing number of `Producers` and by changing events RPS.

Each Game have 10 `Heroes` 5 in one team (slot_0..4) and 5 in another (slot_5..9), each Hero can have upto 6 `Items`. Each Hero can level up. 

**Game consists of four stages:**

1. `Producer` request new game_id and awaits for response (Get request, not event) and send first event "Game started"
2. `Hero` select stage (15 seconds), `Producer`send "Hero selected" events for each slot 
3. Round starts, and `Producers` sends "Round start" event.
4. Round (and Game) ends, respective event sent.

### Events
Each event contain timestamp in miliseconds(int) indicating time passed after game_id aqcuired, event index(int) and game_id(UUIDv7)
- Hero selected: slot_x(int) choose(int) hero_y(hero_id + version_id)
- Item bought: slot_x(int) bought(int) item_y(item_id + version_id)
- Kill: slot_x(int) kill(int) slot_y(int)
- Level Up: slot_x(int) level-up(int) level(int)
- Game started: timestamp linux time(int)
- Round start: no payload
- Game ends: no payload

## Replays
While many ongoing games happen in parallel, system will injest all events, save them to temporary cache and provide in batches to `Workers`. Each `Worker` is responsible for running checks and compiling events together into single bundle, a replay file (binary) and save to database or reporting error to DB.

To make replay file, folowing checks must successed otherwise events are discarded and error recorded to database:
- Game start and Round Start events exist
- hero-to-slot assign events must exists
- Event count equal end game event index - 1

### Bundles
System will occasionally check how many entries exist in replays table, if value is >= current_offset + N (bundle size). N entries are read from DB and packaged into bundle while current_offset incremented by N.

Bundle is a binary file, containing N replays, when packaged into single file, it is saved to CDN and entry created in replay_bundles pointing to that file.

Purpose of bundles, is to reduce DB read load for cross game queries, which will be running on `Administrator` browser.
